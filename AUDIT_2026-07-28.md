# PPA-v2 — Full Application Audit

**Date:** 2026-07-28
**Scope:** Entire codebase — ~50k LOC across 35 pages, 16 edge functions, 304 migrations, 8 locales; Supabase + Stripe + OneSignal/Web-Push. Live on iOS, Android, and web.
**Method:** Static deep-dive across 9 subsystems (build/typecheck/lint, routing, data-layer↔schema, edge functions, Stripe payments, i18n, ranking/ELO, UX/UI, push/realtime). Read-only — no code changed.

> **Important verification caveat:** the Supabase MCP connector did not connect during this audit, so everything below is derived from the **code + the 304 local migrations**. That is authoritative for code-vs-code correctness, but **it cannot see the live database's baseline schema or RLS policies** — and those turn out to matter (see §"What I could not verify"). The migration tree is *not* a complete schema: 154 of 304 files are empty placeholders and no `CREATE TABLE` exists in-tree for the core tables — they and their RLS were applied to the live DB out-of-band. **Several findings below flip between "hardened" and "wide open" depending on live RLS that must be checked directly.**

---

## Overall verdict

The app is **substantially finished and mostly well-built** — navigation is fully wired, the data-access layer is disciplined, the ELO math is sound, the notification pipeline is coherently designed, and the production build is clean. It does **not** have the "half-built, things falling over" feel; the problems are concentrated, not pervasive.

**But there are two areas that need attention before they bite:**

1. **Payments (Critical).** There is **no Stripe payment webhook**. Booking success, amounts, and paid-state are all reconciled *client-side*, and the server never checks the price. On paper this allows underpaying for a court and marking people "paid" without paying — and an abandoned tab can capture money with no booking record. The real blast radius depends on live RLS I couldn't see, so this is the #1 thing to verify.
2. **A committed syntax error in the shared ELO module (Critical-latent).** `_shared/elo.ts` has a duplicated function header. It's harmless *right now* (the deployed edge bundle predates it) but will **break all ELO processing the moment edge functions are next deployed**.

Everything else is High/Medium/Low and listed below in priority order.

Health by subsystem: Build 🟢 · Routing 🟢 · Data-layer 🟢 · Edge functions 🟡 · **Payments 🔴** · i18n 🟡 (non-EN not ready) · **Ranking 🟡→🔴 on deploy** · UX/UI 🟢 · Push/Realtime 🟡

## CRITICAL — fix before anything else

### C1. No Stripe payment webhook → court price is not verified server-side
- **`supabase/functions/create-booking-payment/index.ts:62-116`** only sanity-*caps* the client-sent `amount_pence` (£1–£50/share, ≤£400 total). It never looks up the real court price. `resolve_court_price` is only ever called in the **browser** (`src/pages/BookCourt.tsx:383`). The client sends the amount (`BookCourt.tsx:636`, `PayBooking.tsx:350-362`).
- **Effect:** a caller can pay the £1 minimum per share for a £36 court.
- **Root cause:** `stripe-connect-webhook` only handles `account.updated` (`index.ts:514`; everything else hits "Ignoring event type" at `:556`). There is **no** `payment_intent.succeeded` / `payment_failed` handler anywhere in the repo. All payment success is reconciled client-side.

### C2. Booking confirmation trusts client-set `share_count`, not the amount actually paid
- **`supabase/functions/record-payment/index.ts:635-678`** flips a booking `held → confirmed` when the summed `booking_payments.share_count >= 4`. `share_count` originates from client-supplied PI metadata (`create-booking-payment:100`). The true `pi.amount` is written to the ledger but never compared to price × shares.
- **Effect (with C1):** pay £4, set `share_count=4`, booking flips to `confirmed`.

### C3. `update_paid_player_ids` marks players paid with zero payment check
- **`supabase/migrations/20260718_update_paid_player_ids.sql`** — `SECURITY DEFINER`, `GRANT EXECUTE TO authenticated`. Authorizes only on "is a participant", then writes an **arbitrary** `paid_player_ids` jsonb. No reference to `booking_payments`, no PI check.
- **Effect:** any participant can mark themselves or everyone "paid." Drives the "Already paid" gate (`PayBooking.tsx:249-254`) and the paid dots (`BookingStatus.tsx:149/164/175`).

### C4. Booking row is created client-side *after* payment → abandonment orphans the charge
- **`src/pages/BookCourt.tsx:655-711`** — the PaymentIntent is captured immediately, but the `bookings` row, the ledger write, and the status are all written by the **browser after** Stripe confirms.
- **Effect:** if the tab closes between `confirmPayment` success and those writes: money is captured to the venue, but there's **no booking row, no ledger row, no webhook**, and `process-booking-deadlines` never sees it (it only scans existing `held` rows). `refundBooking` then reads an empty ledger and refunds nothing → **silent money loss with no record.**

### C5. Duplicated function header in the shared ELO module (latent; breaks on next edge deploy)
- **`supabase/functions/_shared/elo.ts:10-11`** — `export function calculateExpected(` appears **twice** in a row. Verified on disk; committed in `0557879` (mtime Jun 26). Deno cannot parse this file.
- **Effect:** `process-elo` and `rebuild-ratings` both import it. The live bundle must predate this commit (that's why ELO still runs today), but the **next `supabase functions deploy` will take down all ELO processing and any rebuild.** One-line fix; do it before any redeploy.

> **Combined caveat for C1–C4:** the `bookings` / `court_bookings` INSERT/UPDATE **RLS policies are not in the repo** (created directly in the remote DB; the local migrations are empty placeholders). If authenticated users can directly insert/update `bookings` with arbitrary `status`/`price`/`paid_player_ids`, the exploits above don't even need Stripe. **Verify these policies against the live DB — this single check determines whether payments are "hardened" or "wide open."**

## HIGH

### H1. The parked career-ELO drift bug — root cause found
- **`src/pages/MatchDetail.tsx:1153-1177`** (`handleDeleteMatch`) and **`supabase/migrations/20260511000004_delete_match_cascade_rpc.sql:27-39`** delete `rating_history` + `match_results` + the match, but **never** decrement `profiles.matches_played` or undo the `internal_ranking`/`peak_elo` that `apply_match_elo` (`20260623000002:88`) applied.
- **This explains the KNOWN_ISSUES symptom exactly:** stored `matches_played`/`internal_ranking` sit *above* a clean rebuild by a **variable per-player amount** (= how many of each player's already-processed matches were later deleted) — matching "Christian 21, Kieran 18, Alex 17 … down to 1", not a uniform −1. The "impossible void counts" are a red herring: void matches are skipped *before* `apply_match_elo` (`process-elo/index.ts:182-194`), so they never contributed to `matches_played`.
- **It is ongoing:** it will re-drift after any rebuild until deletion is made ELO-aware (reverse the deltas / decrement mp, or re-trigger a rebuild on delete). **Do not run `rebuild-ratings` until both this and C5 are fixed** — exactly as KNOWN_ISSUES.md warns.

### H2. Poll confirmation creates matches but sends no notification/push
- **`src/components/polls/PollAdminView.tsx`** — the only notifications sent are `poll_reminder` ("go vote", lines 367/380). The confirm flow (`confirm_poll_schedule` RPC chain: `20260707…`, `20260708…`, `20260710…`, `20260706…`) contains **zero** `INSERT INTO notifications`, and there is no AFTER-INSERT-on-`matches` notification trigger. `match_scheduled` is referenced in the nav/icon code but **never inserted** — a dead type.
- **Effect:** the single most important scheduling event — a weekly availability poll turning into real matches — reaches players **silently** (no bell, no push).

### H3. `process-booking-deadlines` has no trigger in the repo
- The function is cron-guarded (`x-cron-secret === CRON_SECRET`) but nothing schedules it (no `cron.schedule`, no `net.http_post`, no client call — only a deploy comment). Verified.
- **Effect:** this is the money backstop that confirms paid bookings, sends top-up reminders, and **releases + refunds** past-deadline bookings. With no trigger, past-deadline held/underpaid bookings are never auto-released or refunded. **Verify a pg_cron/scheduler job exists in the dashboard.**

### H4. `close-expired-polls` cron is never created in a migration
- **`20260723000001_close_expired_polls.sql:62`** — the `cron.schedule('close-expired-polls', …)` line is **commented out**; `20260723000002` only *assumes* the job exists. Verified: no uncommented scheduling anywhere.
- **Effect:** if that job isn't hand-created in the dashboard, `close_expired_polls()` never runs → expired polls never close **and** the `poll-scheduler` auto-match path (`net.http_post`, `mode:'auto'`) never fires. The entire auto-scheduling feature silently no-ops. **Verify in dashboard.**

### H5. Event payment has the same client-side-reconciliation orphan gap as C4
- **`src/pages/VenueEventDetail.tsx:496-511`** → `finaliseEventPayment` → `join_venue_event` RPC. The PI + a `pending` `order_items` row are created, then the spot is reserved client-side after `confirmPayment`. No webhook, **no reconciliation job for `pending` order_items.** Abandon after paying → charge captured, `order_items` stuck `pending`, no spot. The finalize RPC is SQL and cannot verify the PI with Stripe.

### H6. No idempotency keys on PaymentIntent creation
- `create-booking-payment:107` and `create-event-payment:272` call `stripe.paymentIntents.create(...)` with no `idempotencyKey`; the event path also creates a fresh `order_items` row per call. A retried `initPayment` mints duplicate PIs/rows.

### H7. Concurrent share payments are unguarded (double-charge)
- **`PayBooking.tsx:286-322`** — two people opening the pay link simultaneously both see a share as unpaid and can both pay it. The unique index is on `stripe_payment_intent_id` only (`booking_payments_ledger.sql:25`), so different PIs for the same covered player aren't deduped. Both charges capture; only the display dedups.

### H8. i18n: entire competitive surface is English-only for non-English users
- **610 leaf keys (39%) are missing from *every* non-English locale** (es/fr/it/pt/sv/ar/hi are all frozen at ~967 keys while `en` has 1,577). Missing exactly the recently-wired features: `league` 220, `match` 190, `polls` 77, `ranking` 45, `play` 25, `group_detail` 24, `community` 17.
- **Effect:** League, Match-detail, Polls, and Ranking fall back to raw English in all 7 non-English languages. The framework (config/fallback/persistence/switcher) is correct — only the translations are missing.

### H9. i18n: zero RTL support — Arabic layout will break
- `index.html` is `lang="en"` and never updated; there is **no `dir="rtl"`** anywhere in the codebase. Arabic ships but renders LTR (alignment, icons, layout broken). Arabic plural categories are also unsupported (`en` defines only `_one`/`_other`; CLDR Arabic needs zero/one/two/few/many/other).

### H10. i18n: `BookCourt.tsx` (2,248 lines) has zero `t()`
- The entire court-booking flow is hardcoded English for **everyone**, in every language. (Also overlaps the payment findings — this is the highest-traffic un-translated page.)

## MEDIUM

### Data / schema
- **M1. Phantom RPC `resolve_court_price`** — no definition anywhere in the repo (`BookCourt.tsx:383`). Degrades gracefully (pricing silently never shows), but is either applied out-of-band or a dead feature. Verify in live DB. *(This is also the root of C1 — pricing has no server authority.)*
- **M2. Venue-events subsystem lives outside the migration tree.** `join_venue_event`/`leave_venue_event` are defined only in the loose `supabase/venue_events_rls_and_rpcs.sql`; the tables `venue_events`, `venue_event_occurrences`, `venue_event_participants`, `order_items` have **no `CREATE TABLE` in any tracked file**. Works on the live DB only if applied manually; a DB rebuilt from `migrations/` alone would have this feature broken. Reproducibility risk.

### Edge functions
- **M3. Two payment functions trust the payer identity from the request body** — `create-event-payment:35` reads `user_id`; `create-booking-payment` reads `booker_id`/`player_id`. Neither calls `getUser()`. Payment mis-attribution/spoofing (amounts are validated vs Stripe, so not price tampering here).
- **M4. Cron-secret naming is inconsistent** — `poll-scheduler` reads `POLL_CRON_SECRET`, `process-booking-deadlines` reads `CRON_SECRET`; poll auto-mode also needs a vault secret `poll_cron_secret` to equal the function env or it 401s. Fragile coupling.
- **M5. `notify-onesignal` and `process-elo` depend on dashboard DB webhooks not in version control.** A project replay wouldn't recreate ELO processing or native push. `notify-onesignal` also **fully duplicates** `send-push` (both fire on `notifications` INSERT).

### Push / realtime
- **M6. Two dead realtime subscriptions on `league_standings`** — the table was never added to the `supabase_realtime` publication (`20260511000006` adds the others). `LeagueDetail.tsx:2210` live standings never fire; `TournamentMode.tsx:234` subscribes only to that table → **tournament standings never live-update at all.** One-line fix: `ALTER PUBLICATION supabase_realtime ADD TABLE league_standings;`
- **M7. Booking pushes fire but dead-end on tap** — `booking_topup_reminder`/`booking_released` (`process-booking-deadlines:104/120`) have no `booking_*` case in `compute_notification_nav_url()` or `getNavTarget()`, so a time-critical "top up before your court is released" push lands the user on a generic list instead of the booking.

### Ranking
- **M8. Client "points at stake" preview omits the server's dominant-win 1.1× multiplier** (`eloPreview.ts:31-49` vs `_shared/elo.ts:26-44`). Preview understates a dominant-win award by ~10%.
- **M9. Super-tiebreak encoding can void a real result** — a single-set/championship super-tiebreak stored as games `1-0` classifies `isVoid` → the whole match is dropped from career ELO (and from set-as-match leagues). Also `scoreValidation.isValidStandardSet` would *reject* a `10-8` super-tiebreak that `classifyKernel` treats as completed — validator/classifier inconsistency. Verify how the entry UI encodes deciding super-tiebreaks.

### Payments
- **M10. `paid_player_ids` unreliable for guest / logged-out payers** — `update_paid_player_ids` requires `auth.uid()`, but `PayBooking` is a public anon-key page. Guests' call silently fails, so a paid guest shows "Payment pending" in `BookingStatus`.
- **M11. Booking payments are hard-coded GBP** (`create-booking-payment:109`; `money.ts formatPence` is £-only). Any non-UK venue that became bookable would be charged/shown in GBP. Latent (only TPT Bristol is bookable today). The event flow *is* correctly multi-currency.
- **M12. `ppa_bookable` can go stale** if a venue's charges are later disabled (the gate trigger only fires on `padel_venues` writes, not on the webhook flipping `charges_enabled`). Mitigated: `create-booking-payment:83` re-checks live at pay time, so payment is blocked — but the venue keeps showing as bookable in listings.

### UX / correctness
- **M13. `window.confirm()` / `confirm()` for destructive actions** — `You.tsx:1558`, `EventDetail.tsx:174`, `LeagueDetail.tsx:1188/1281/3153/3268`. Native dialogs are unstyled and can be suppressed by some in-app webviews (action may silently proceed or be unreachable on mobile). Should use the app's own modal.
- **M14. Connect/Accept mutations have no `onError`** — `AllPlayersPage.tsx:55/70`, `PlayerProfile.tsx:~223`. A failed connection request re-enables the button with zero feedback. App-wide: 64 `useMutation` vs 56 `onError`.
- **M15. Misleading empty-on-failure** — many `useQuery` screens ignore `isError` (`OpenMatches:24`, `Notifications:124`, `VenueDetail` secondary, `PlayerProfile:156-208`, `AllPlayersPage`, `MyConnectionsPage:25`, `RewardsCard:79/92`). A network error looks identical to "you have nothing here."
- **M16. Real i18n bug — raw key rendered to users** — `GroupDetail.tsx:1065/1067` call `t('group_detail.save_failed')` / `t('group_detail.settings_saved')`; those keys don't exist in `en` and there's no `defaultValue`, so the toast shows the literal string `group_detail.save_failed` in **all** languages.
- **M17. `AllPlayersPage.tsx:21`** calls `setState` synchronously inside a `useEffect` (real eslint error: `react-hooks/set-state-in-effect`) → cascading re-renders.

### Process
- **M18. CI does not actually gate quality.** The CI "Typecheck" step runs `npx tsc --noEmit`, which — with this repo's project references — sees **no files** and passes vacuously; only the Build step (`tsc -b`) truly typechecks. Lint runs with `continue-on-error: true`, so its 273 errors never block a merge. (Local `tsc -b` build is clean — this is about the gate, not current state.)

## What's MISSING / DISCONNECTED (thematic view)

- **Server-side payment truth** — no payment webhook, no server price authority, no reconciliation of abandoned charges (booking *or* event). This is the single biggest structural gap.
- **Two scheduled jobs with no in-repo trigger** — `process-booking-deadlines` (refunds/releases) and `close-expired-polls` (which also gates auto-scheduling). Both must be confirmed in the dashboard or they silently no-op.
- **Poll-confirmation notifications** — the auto-scheduling feature's payoff moment produces no user signal.
- **Non-English delivery** — 39% of strings untranslated everywhere, plus no RTL and an un-translated booking flow. The plumbing is done; the content isn't.
- **Reproducibility** — the base schema, core-table RLS, venue-events tables/RPCs, and two DB webhooks live only in the remote DB, not in `migrations/`. A rebuild from the repo would not reproduce the app.

### Live verification — partial (2026-07-28, via anon-key read-only REST)

Ran non-destructive `GET`s / a read-only RPC against the live project with the public anon key (no writes, no service_role). Results:

- **Read-side RLS is enforced.** `profiles`, `bookings`, `court_bookings`, `booking_payments`, `order_items`, `notifications` all return `[]` to the anon role (a live app's `profiles` is never truly empty → RLS is filtering). So these tables are **not publicly readable.** ✅
- **`resolve_court_price` RPC EXISTS** and is deployed (returned a structured `{status:"not_configured", price_pence:null, …}` for a dummy venue). **Downgrades M1** from "phantom/possibly dead" to "real, applied out-of-band (reproducibility caveat only)."
- **`padel_venues` carries server-side price columns** — `price_pence`, `price_per_player_pence`, `price_per_hour`, `typical_court_price_offpeak/peak`, `ppa_bookable`, `currency`. **This strengthens C1:** the authoritative price *is* available server-side; `create-booking-payment` simply doesn't check the client amount against it. (`padel_venues` PK is `venue_id`, not `id`.)
- **Venue-events tables are real** — `venue_events` and `venue_event_occurrences` return live rows. **M2 tables confirmed to exist** in the live DB (defined out-of-band; reproducibility caveat stands).

**Still NOT verifiable without arbitrary-SQL (MCP `execute_sql`):** write-side RLS on `bookings`/`court_bookings` (the core C3/C4 question — anon *read* being blocked says nothing about authenticated *insert/update* policies); `cron.job` entries for `process-booking-deadlines` and `close-expired-polls` (H3/H4); the `notify-onesignal`/`process-elo` DB webhooks (M5); and whether `league_standings` is in the `supabase_realtime` publication (M6). These need `pg_policies` / `cron.job` / `pg_publication_tables`, which PostgREST does not expose.

## Recommended fix order

1. **Verify live `bookings` RLS** (settles the true severity of C1–C4). *(dashboard/DB — minutes)*
2. **Fix `_shared/elo.ts` duplicate header (C5)** — one line, before any edge deploy.

5. **Make match deletion ELO-aware (H1)**, *then* run `rebuild-ratings` to clear the accumulated drift.
6. **Wire poll-confirmation notifications (H2)** and add `league_standings` to the realtime publication (M6).
7. **i18n:** backfill the 610 missing keys, add RTL + `lang`/`dir`, translate `BookCourt.tsx`, fix `group_detail.save_failed` (H8–H10, M16).
8. UX polish: replace `window.confirm` (M13), add mutation `onError` + query error states (M14, M15).
9. Housekeeping: delete dead code, fix the CI typecheck/lint gate (M18), guard `rebuild-ratings`.
